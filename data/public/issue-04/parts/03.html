open-code-review

GitHub 上的开源项目，阿里巴巴把内部用了两年的 AI 代码审查工具开源了（README 称服务过数万名开发者）。它读你的 Git 改动，先按规则挑出要审的文件，再交给 AI 细查，最后给出精确到行的意见。命令行工具叫 ocr，也能装进 Claude Code、Codex、Cursor，或接进 GitHub Actions 自动跑。

它能做什么

  • ocr review 审本地还没提交的改动；也能审一个分支相对 main 的全部改动，或者单个提交。
  • ocr scan 不看改动，直接把整个仓库或某个目录从头扫一遍。
  • 内置多种语言的审查规则，比如空指针、线程安全、XSS（网页注入攻击）、SQL 注入；规则可以按路径自己调。
  • 委托模式（Delegation Mode）：挑文件、配规则由它来做，审查交给你正在用的 AI 工具，不用另配模型密钥。结果可以存成 JSON，交给 AI 接着修。

最突出的点

死板的活交给程序，灵活的活交给 AI

通用 AI 审大改动时爱偷懒，只看几个文件，行号还常对不上。它把「审哪些文件、哪些文件一起看、套哪条规则、意见落在哪一行」都用固定程序管住，AI 只负责判断。README 公布的对比：同一个模型下误报更少，token 用量约为通用 Agent 的 1/9。

适合谁用

自己写代码、或让 AI 写代码，却没人帮忙审的独立开发者；想在合并前多一道自动检查的小团队。

缺点与应对

  1. 缺点1：它故意少报。README 写明它的查全率（Recall）低于通用 Agent，用这个换更少的误报。 应对：把它当第一道筛子。登录、权限、支付这类关键代码，人还要亲自看一遍。
  2. 缺点2：默认模式要配自己的模型和密钥，改动的代码会发给你选的模型服务。 应对：私密代码选可信的模型服务；或者用委托模式，让你已经在用的 AI 工具来审。密钥只填进它的配置向导或环境变量。
  3. 缺点3：对 Git 版本有要求，支持哪些语言要自己试。前置条件写明 Git ≥ 2.41；README 没列出完整的语言清单。 应对：先运行 git --version 确认版本；冷门语言先跑一次看意见质量，不理想就只用它审后端代码。
技术含金量

价值在于「确定性工程 + Agent」的分工：必须不出错的步骤（挑文件、分组、配规则、定位到行）用普通程序写死，需要判断的部分交给 AI。大改动拆成几组，每组交给一个独立的子 Agent，彼此上下文不干扰，改动再大也稳。

它还公开了评测集 AACR-Bench：50 个热门开源仓库的 200 个真实 PR，80 多位资深工程师标注了 1,505 个真问题。给 AI 工具做评测先备好人工标注的标准答案，这点和本期 modern-web-guidance 的做法一致。

技术关联

① 热门技术取舍：第三期的 pr-agent 擅长在 GitHub 的 PR 页面里对话式审查；open-code-review 擅长在本地命令行和 CI 里批量、精确地审。想在 PR 页面里看 AI 点评，用 pr-agent；想合并前在本地跑一遍、结果存成 JSON 让 AI 接着修，用 open-code-review。两个都接进 CI 会重复评论，选一个就好。
