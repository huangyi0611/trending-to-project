auto-ontology

NVIDIA 在 GitHub 上开源的语义层工具。它先读你的数据库，整理出一份「业务词典」（Ontology：每个业务词是什么、表和表怎么关联、指标怎么算），人确认后再交给 Agent 去查数。每个答案都附上查询语句（SQL）和步骤；数据覆盖不到的问题，它会直接说「答不了」。后端用 FastAPI + Postgres，可以通过 MCP、API 或自带的 skill 接进你的 AI 工具。

它能做什么

  • 读数据库的表结构、样本数据和历史查询，整理出业务词、表之间的关系和能反复用的计算公式（SQL），存进 Postgres（用 pgvector 做相似内容搜索）。
  • 人在界面里核对、修改，再「认证」这些定义；之后谁问「收入」「客户」，都按同一套公式算。
  • 把你用日常语言问的问题翻成 SQL 去查（Text-to-SQL），返回答案、SQL 和推理步骤；还能先用 check_answerable 看看这个问题数据能不能答。
  • 可以通过 MCP、REST API 或三个官方 skill（安装 / 管理 / 查询）接进你现有的 AI 工具。默认用 NVIDIA NIM 跑模型，也能换成其他兼容 OpenAI 格式的模型服务。

最突出的点

先把「词」认准，再让 AI 去查数

它解决的问题是：AI 给的数字靠不靠谱。定义由人确认过，答不上来就明说，用到的 SQL 也摆出来给你核对。比让模型直接对着原始数据表自由发挥稳得多。

适合谁用

手上有表格或数据库、想让 AI 帮忙查数，却常遇到「同一个指标两种算法」的人。也适合想给读书笔记、知识库先建一份术语表的人，比只把原文切成小段去搜更准。

缺点与应对

  1. 缺点1：它是一整套平台，体量大。要同时跑网页前端（Next.js）、两个 FastAPI 服务和 Postgres 数据库，还要模型密钥；在自己电脑上用 Docker Compose 一键启动也要花些功夫。 应对：先学它的思路，不必整套搬进正式产品。一般的小产品或内容项目只抄三步就够：整理术语 → 人确认定义 → 答不了就说答不了。真想试，用官方的 Docker Compose 和示例数据库跑通聊天功能，再决定接不接自己的数据。
  2. 缺点2：默认的安全设置要盯紧。仓库写明 3001、3002 这两个端口只能放在内网；负责导入数据的服务几乎不验证身份，直接相信前端转过来的用户信息。打开可选的 KumoRFM 预测功能后，还会把表里的数据上传到对方服务器。 应对：对外只开 3000 端口，后端端口别暴露到公网。数据没审查完之前，不要填 KUMO_RFM_API_KEY。密钥和数据库密码按官方说明改掉默认值。
  3. 缺点3：不收外部代码贡献，也要留意绑定某一家模型服务。维护完全由 NVIDIA 团队负责；默认模型走 NIM，不过可以换。 应对：把它当一份能跑的参考样板来学，别指望给它提 PR 一起共建。需求和 bug 通过 issue 反馈。自己部署时先配好自己的模型服务地址，免得整个流程只能用一家的云端模型。
技术含金量

价值在于给 AI 一份大家公认、可以核对的背景资料。AI 会查数据库、会写 SQL，可如果「收入」在两个系统里算法不同，查得再快也没用。这个项目把术语、关系和认证过的计算公式放在第一位，每个答案都带出处。

流程也清楚：先生成草稿 → 人认证 → 再回答。常见做法是把整个数据库的表结构（schema）塞给模型碰运气，它反过来先定规矩。它还把「预测未来」和「查已有数据」分开处理（预测可选用 KumoRFM），这种分拣本身就值得学。

技术关联

① 热门技术取舍：只用 RAG（把文档切成小段再搜），适合文章、PDF 这类没有固定格式的资料；只把原始表结构喂给模型，起步快，但指标口径会越用越乱。完整的 Auto Ontology 适合多个系统、要求口径统一的查数场景。个人项目多数用不上整套平台，先做术语表和「答不了就拒绝」更划算，图谱可视化以后再说。仓库还说能和 Apache Ossie（一种交换语义模型的格式）互相导入导出，等你以后要跨工具共享再看。
