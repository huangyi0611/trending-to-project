OpenMausBot

GitHub 上的开源项目，功能对标 xAI 的同类 AI 助手产品：在一个聊天应用里管理一队 Agent。每个 bot 可以换模型，也可以有自己的电脑（云桌面、本机里的虚拟机，或经你确认后直接用本机），危险操作要你点「允许」。默认数据存在本机（local-first，放在 ~/.openmausbot 文件夹），可以接你电脑上已登录的 Claude Code、Codex、Grok 命令行工具。桌面端用 Electron 开发。

它能做什么

  • 把多个 bot 当联系人管理：每个 bot 的人设、模型、电脑、连接的应用都可以不同。
  • 跑命令、改文件这类有风险的动作，会变成聊天里的「允许 / 拒绝」卡片。
  • 可以通过 Composio 这类连接器接 Gmail、Slack、GitHub 等（授权给多大权限要自己把关）。
  • 支持用一份 Markdown 文件（「团队包」）一次导入整组 bot、频道和建议的定时任务；也能分享部门模板（不含密钥和聊天记录）。

最突出的点

像通讯录一样管一队 AI

它把「一个全能助手」拆成能分工的一队人，默认数据和密钥都留在本机。如果你已经在用托管式的 AI 助手产品，想看看开源版怎么做「成员列表 + 审批 + 电脑」，这个仓库很适合对照。

适合谁用

想在自己电脑上跑多个角色的 AI、又需要审批关卡的人。做协作产品的人，也可以只借鉴它「邀请 / 分享部门 / 权限卡片」的产品设计。

缺点与应对

  1. 缺点1：体量大，未解决的 issue 约 981 个，功能边界还在变。比如 README 写明，Ubuntu 在 Wayland 桌面下的本机控制功能，因为一个 issue 暂时关闭。 应对：先当产品参考、在本机试用，别一上来就改它的核心当自己的后端。关注版本发布（releases）和安全说明（SECURITY），正式用之前只给最小权限。
  2. 缺点2：许可证是 open-core。删掉 enterprise/ 目录后才是纯开源软件（OSS）；企业目录另有许可，正式使用其中的功能要授权。 应对：自用或二次开发前，先确认没用到 enterprise 目录。要分发或替别人托管前，读一遍 LICENSING.md；它的商标名也不能直接拿来当自己的产品名。
  3. 缺点3：控制本机和连接第三方账号的权限很大。bot 一旦拿到你的电脑和邮箱，误点一次「允许」代价不小。 应对：保持默认的「先问再做」；本机控制只在你主动打开后才生效。连接器一个一个开，定期检查授权。正式环境的密钥别靠在聊天里粘贴一次来管理。
技术含金量

价值在产品骨架：多个 bot、每个 bot 一台电脑、危险动作变成卡片、团队配置能打包分享且默认不带密钥。这些比再包一层聊天接口难做得多。

「数据存本机 + 本机运行的 harness」也值得看：程序和对话记录（transcript）都留在你自己电脑上，云端只是一台可选的电脑，数据以本机为准。

技术关联

① 热门技术取舍：只需要一个写代码的 AI，继续用 Cursor 或 Claude Code 就行。要「一队分好角色的助理 + 审批」，才值得装这类桌面应用。别和本期的 agent-browser、第二期的 agent-desktop 叠成三套电脑控制工具，先定场景再装。
