skills

GitHub 上的开源项目，Matt Pocock 公开的日常工程 skill 合集，自称「给真在做产品的人用，不搞 vibe coding」。每个 skill 都小、能改、能组合，用来追问需求（grill）、共建词汇表、先写测试再写代码（TDD）、排查 bug、检查代码结构。和第二期的 anthropics/skills 的区别：那个是官方的 skill 写法样板，这个是一套能直接调用的工程菜谱。

它能做什么

  • 你主动调用的：/grill-with-docs、/to-spec、/to-tickets、/implement、/triage 等，把「先问清楚再动手」变成固定流程。
  • 模型会自动调用的：/tdd、/diagnosing-bugs、/code-review、/codebase-design 等守规矩的步骤。
  • 强调项目里的共享语言：把行话写进 GLOSSARY.md 和 ADR，免得 AI 每次用 20 个词解释一个概念。
  • 能装进 Claude Code、Codex、Copilot、Gemini CLI 或其他 AI 工具。官方说明：插件方式会自动更新，skills.sh 方式复制的是能改的文件，两种别同时装，否则会重复。

最突出的点

先对齐说法，再让 AI 写代码

作者把常见的失败说得很直白：没对齐、太啰嗦、没反馈、系统越改越乱。他给的办法都是老功夫：追问（grilling）、词汇表、「红灯 → 绿灯 → 重构」的测试节奏、定期检查模块设计。

适合谁用

已经会用 AI 改代码，但经常「做出来不对」或「代码越来越难改」的人；尤其是有很多自己业务词（比如会员等级、订单状态）的产品。

缺点与应对

  1. 缺点1：skill 很多，全打开反而成了新负担。作者自己也在批评 GSD、BMAD、Spec-Kit 这类「接管整个开发过程」的方法。 应对：每个仓库先跑一次 /setup-matt-pocock-skills，只留追问、词汇表、TDD、代码审查这几个，其他的等真遇到问题再加。
  2. 缺点2：容易和官方 skill 规范、其他 skill 包重复安装。 应对：skill 的目录结构继续按 anthropics/skills 或你自己的 SKILL.md 规范来；这套只当「怎么做事」的菜谱。同名命令先看会不会覆盖你已有的 skill。
  3. 缺点3：旧代码的问题它解决不了。仓库写明 /improve-codebase-architecture 只负责找问题，老代码不会被自动理顺。 应对：把它的结果当候选清单，每次只改一处值得深挖的模块。别指望一条命令把整个仓库重整一遍。
技术含金量

价值在于把工程基本功变成能重复执行的动作。共享语言（接近领域驱动设计里的「统一语言」）能同时省 token、减少命名混乱；TDD 给 AI 一个不会跑偏的反馈；「深模块」（出自《A Philosophy of Software Design》一书）用来对付「AI 写得越快，代码烂得越快」。

它故意做得小、能组合，没有再做一个包揽全部流程的大系统，和「一个 skill 只做一件事」的原则一致。

技术关联

① 热门技术取舍：只需要官方 skill 目录结构，用第二期的 anthropics/skills。只需要设计审美，用 hallmark 或 impeccable。想解决「每天怎么和 AI 对齐」，用这一套。三个流程框架别叠在一起用。
