pr-agent

GitHub 上开源的 PR 审查 Agent：在 PR 下面用 /review、/describe、/improve、/ask 等命令，自动写说明、提审查意见和改进建议。可以放进 GitHub Actions 跑、当 CLI 用，或者部署在自己的服务器上，也支持 GitLab、Bitbucket、Azure DevOps 等平台。仓库写明：这是社区维护的开源项目，和 Qodo 公司的免费版、托管产品是两回事。

它能做什么

  • PR 新建或更新时自动审查；也可以在评论里手动发命令。
  • 遇到改动很大的 PR，按文档里的压缩办法处理，不会把全部改动（diff）硬塞给模型。
  • 通过 LiteLLM 切换 OpenAI、Claude、Gemini、Ollama 等模型。
  • 提示词和审查类别都能在配置文件里改，方便放进团队自己的审查清单。

最突出的点

AI 先审一遍，合并按钮还在人手里

它让每条 PR 都先有一份能读懂的审查意见；机器说「没问题」也不代表可以合并。这正好对应「AI 可以改代码、提 PR，合并和上线必须人确认」的规矩。

适合谁用

已经让 AI 提 PR、需要一条稳定的自动预审流程，又希望代码只经过自己的模型密钥或自己部署的服务的人。

缺点与应对

  1. 缺点1：AI 审查会漏，也会误报，不能当合并许可。 应对：只把它当第一轮意见。合并前仍按你的清单人工确认（状态流转、登录验证、权限这些关键地方尤其要看）。
  2. 缺点2：代码会发给你配置的模型服务商。自己部署也不等于数据不出门。 应对：读仓库里的 Data Privacy（数据隐私）说明。敏感项目用自己控制的模型地址（或本地模型），限制 Action 密钥的权限范围，别让私钥出现在日志里。
  3. 缺点3：有已知的安全注意事项，名字也容易和商业产品搞混。比如 README 写明，/help_docs 命令从 v0.36.1 版起因为可能泄露凭据暂时关闭（issue #2445）；Docker 镜像的名字也换过。 应对：别开已经关闭或没修好的命令；锁定检查过的版本，镜像名用 pragent/pr-agent（0.34.2 及以上）。开源的 PR-Agent 和 Qodo 的托管产品要分开配置。
技术含金量

价值在于能接进现有的 Git 流程：一条命令、大 PR 能压缩、提示词能改、模型能换。比起再做一个聊天里的审查机器人，它更贴近团队平时的做法。

它也提醒你分清产品边界：开源的老项目和公司托管的产品已经分家了。选工具前先想好，你要自己部署，还是要商业平台。

技术关联

① 热门技术取舍：只是自己偶尔看看改动，编辑器自带的审查或人工看就够。PR 多、希望评论区格式统一，再装 pr-agent。GitHub 官方或其他商业审查工具功能更全，但数据去向和价格不同，按隐私要求和预算选一个主工具。
