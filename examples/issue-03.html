auto-ontology


NVIDIA 在 GitHub 上开源的语义层工具。它先读你的数据库，整理出一份「业务词典」（Ontology：每个业务词是什么、表和表怎么关联、指标怎么算），人确认后再交给 Agent 去查数。每个答案都附上查询语句（SQL）和步骤；数据覆盖不到的问题，它会直接说「答不了」。后端用 FastAPI + Postgres，可以通过 MCP、API 或自带的 skill 接进你的 AI 工具。

它能做什么


    

  • 读数据库的表结构、样本数据和历史查询，整理出业务词、表之间的关系和能反复用的计算公式（SQL），存进 Postgres（用 pgvector 做相似内容搜索）。
    • 

  • 人在界面里核对、修改，再「认证」这些定义；之后谁问「收入」「客户」，都按同一套公式算。
    • 

  • 把你用日常语言问的问题翻成 SQL 去查（Text-to-SQL），返回答案、SQL 和推理步骤；还能先用 check_answerable 看看这个问题数据能不能答。
    • 

  • 可以通过 MCP、REST API 或三个官方 skill（安装 / 管理 / 查询）接进你现有的 AI 工具。默认用 NVIDIA NIM 跑模型，也能换成其他兼容 OpenAI 格式的模型服务。
    • 









最突出的点


先把「词」认准，再让 AI 去查数


它解决的问题是：AI 给的数字靠不靠谱。定义由人确认过，答不上来就明说，用到的 SQL 也摆出来给你核对。比让模型直接对着原始数据表自由发挥稳得多。






适合谁用


手上有表格或数据库、想让 AI 帮忙查数，却常遇到「同一个指标两种算法」的人。也适合想给读书笔记、知识库先建一份术语表的人，比只把原文切成小段去搜更准。










缺点与应对


    

  1. 缺点1：它是一整套平台，体量大。要同时跑网页前端（Next.js）、两个 FastAPI 服务和 Postgres 数据库，还要模型密钥；在自己电脑上用 Docker Compose 一键启动也要花些功夫。
          应对：先学它的思路，不必整套搬进正式产品。一般的小产品或内容项目只抄三步就够：整理术语 → 人确认定义 → 答不了就说答不了。真想试，用官方的 Docker Compose 和示例数据库跑通聊天功能，再决定接不接自己的数据。
    2. 

  2. 缺点2：默认的安全设置要盯紧。仓库写明 3001、3002 这两个端口只能放在内网；负责导入数据的服务几乎不验证身份，直接相信前端转过来的用户信息。打开可选的 KumoRFM 预测功能后，还会把表里的数据上传到对方服务器。
          应对：对外只开 3000 端口，后端端口别暴露到公网。数据没审查完之前，不要填 KUMO_RFM_API_KEY。密钥和数据库密码按官方说明改掉默认值。
    3. 

  3. 缺点3：不收外部代码贡献，也要留意绑定某一家模型服务。维护完全由 NVIDIA 团队负责；默认模型走 NIM，不过可以换。
          应对：把它当一份能跑的参考样板来学，别指望给它提 PR 一起共建。需求和 bug 通过 issue 反馈。自己部署时先配好自己的模型服务地址，免得整个流程只能用一家的云端模型。
    4.

技术含金量



价值在于给 AI 一份大家公认、可以核对的背景资料。AI 会查数据库、会写 SQL，可如果「收入」在两个系统里算法不同，查得再快也没用。这个项目把术语、关系和认证过的计算公式放在第一位，每个答案都带出处。


流程也清楚：先生成草稿 → 人认证 → 再回答。常见做法是把整个数据库的表结构（schema）塞给模型碰运气，它反过来先定规矩。它还把「预测未来」和「查已有数据」分开处理（预测可选用 KumoRFM），这种分拣本身就值得学。







技术关联



① 热门技术取舍：只用 RAG（把文档切成小段再搜），适合文章、PDF 这类没有固定格式的资料；只把原始表结构喂给模型，起步快，但指标口径会越用越乱。完整的 Auto Ontology 适合多个系统、要求口径统一的查数场景。个人项目多数用不上整套平台，先做术语表和「答不了就拒绝」更划算，图谱可视化以后再说。仓库还说能和 Apache Ossie（一种交换语义模型的格式）互相导入导出，等你以后要跨工具共享再看。

最突出的点


人和 AI 共用同一个零件盒


组件库很多，它的特别之处是规矩统一、文档齐全，AI 才能猜准下一个组件该怎么用。只给模型看截图或零散例子，很难做到这一点。






适合谁用

缺点与应对


    

  1. 缺点1：只适用于 React 网页。它是 React 组件，放不进 iOS、Android 原生工程。
          应对：别为了追热度把原生 App 改写成 React。可以抄的是：统一命名、统一的组件参数（props）写法、给 AI 一份「什么场景选哪个组件」的短文档。以后做 React 网页时，再考虑引入。
    2. 

  2. 缺点2：还在 Beta 测试期，未解决的 issue 约 691 个。图表等包还标着 canary，稳不稳定要自己判断。
          应对：正式使用先锁定版本号，只装真正用到的包（core 加一个主题）。关注更新日志（changelog），开源不等于稳定。
    3. 

  3. 缺点3：swizzle 之后容易和官方版本走散。源码复制进你的仓库后，官方修的 bug 不会自动同步过来。
          应对：能用主题变量和 className 改的，就别 swizzle。真复制出来了，记下改了哪几个文件、为什么改，并安排好以后怎么跟上官方版本。

技术含金量



好的设计系统省掉的是「每次从零猜界面」的功夫。对 AI 尤其明显：命名、参数、组合方式一致，生成的结果才可预期。Astryx 把给人看的文档和给 AI 用的 CLI 做成同一套，方向是对的。

缺点与应对


    

  1. 缺点1：体量大，未解决的 issue 约 981 个，功能边界还在变。比如 README 写明，Ubuntu 在 Wayland 桌面下的本机控制功能，因为一个 issue 暂时关闭。

    2. 

  2. 缺点2：许可证是 open-core。删掉 enterprise/ 目录后才是纯开源软件（OSS）；企业目录另有许可，正式使用其中的功能要授权。
          应对：自用或二次开发前，先确认没用到 enterprise 目录。要分发或替别人托管前，读一遍 LICENSING.md；它的商标名也不能直接拿来当自己的产品名。
    3. 

  3. 缺点3：控制本机和连接第三方账号的权限很大。bot 一旦拿到你的电脑和邮箱，误点一次「允许」代价不小。
          应对：保持默认的「先问再做」；本机控制只在你主动打开后才生效。连接器一个一个开，定期检查授权。正式环境的密钥别靠在聊天里粘贴一次来管理。

它能做什么


    

  • wt switch -c：新建分支和 worktree 并进入文件夹；加上 -x claude 还能马上启动 AI。
    • 

  • wt list：查看每个 worktree 改了什么、比主线（main）多了哪些提交；还支持拉取 PR、合并和清理。
    • 

  • hooks：创建、合并前后自动装依赖、启动本地开发服务等。
    • 

  • 在 APFS、btrfs、XFS 这类支持写时复制的磁盘上，多个 worktree 可以共用 node_modules、target/ 这类缓存文件夹，不用每次重新安装。
    • 









最突出的点


给每个并行的 AI 分一张工位


git 自带的 worktree 能用，但命令长、路径难记。Worktrunk 把「给每个 AI 一张干净桌子」变成几句日常口令。同时开 5–10 个任务时，这是最先让人头疼的地方。






适合谁用


已经在电脑上同时跑好几个 Claude Code、Codex 或 Cursor Agent，却还在手敲 git worktree add 的人；只用一个 AI 改一个项目的，可以先不装。










缺点与应对


    

  1. 缺点1：又要学一套命令，可能和你的 shell 别名、编辑器自带的 worktree 功能冲突。
应对：只在真要并行的项目里用；先学会 switch / list / remove 三个命令。Windows 上它和系统自带的 wt（Windows Terminal 终端）重名，可以改用 git-wt，或关掉冲突的别名。
    2. 

  2. 缺点2：共享缓存要看磁盘格式。磁盘不支持写时复制（CoW）时，「瞬间装好依赖」的效果出不来。
          应对：先查官方文档支不支持你的磁盘格式。不支持就每个 worktree 各自装依赖，或者把项目放到 APFS / btrfs 磁盘上再试。
    3. 

  3. 缺点3：多条线怎么合并，还得人来定顺序。工具只管工位，不管产品决策；几个 AI 同时改同一块代码，照样会冲突。
          应对：按模块分任务；合并前用 wt list 或 PR 检查一遍。比如「登录功能一条 worktree、支付流程另一条」，避免两边改同一个文件。
    4.

它能做什么


    

  • open（打开）→ snapshot（拍快照）→ click @e1（点击）这样的短循环；编号失效时会要求重新拍快照。
    • 

  • 点击前先检查元素是否被挡住、能不能点，失败就直接报错，不会假装成功。
    • 

  • 能截图、录屏、管理 cookie 和登录状态；支持同时开多个 session、使用云端浏览器服务，以及 iOS 模拟器里的 Safari 等（见文档）。
    • 

  • agent-browser skills get core 能取出和当前版本匹配的操作说明，避免「说明书和程序版本对不上」。
    • 









最突出的点


让 AI 看网页的结构图


纯看截图、按坐标点，费 token 又容易点歪。用无障碍树加固定编号，更省 token，也更容易写成固定脚本。它和第二期的 agent-desktop（桌面版无障碍树）是同一个思路，搬到了浏览器上。






适合谁用


想让 AI 打开网页做验收、填表、抓公开网页结构的人。它对原生 iOS 界面自动化支持有限（文档里有模拟器的用法可以试）。










缺点与应对


    

  1. 缺点1：未解决的 issue 约 562 个，功能面很宽，最容易踩坑的是权限和登录状态。
应对：先跑通 open / snapshot / click / close 四步。涉及登录时用官方的 session / auth（登录管理）功能，并设好允许访问的网站名单；别让 AI 拿着已登录的浏览器随便逛。
    2. 

  2. 缺点2：编号会过期。页面一跳转或内容一变（DOM 变了），旧的 @e1 就失效了。
          应对：每次跳转后重新 snapshot。写 skill 时把「先快照再操作」写成必做步骤，和官方的 core skill 保持一致。
    3. 

  3. 缺点3：它干不了所有爬虫的活，也替代不了后端 API。遇到反爬、强验证码、纯画布（canvas）做的网页，还是很难办。
          应对：能调官方 API 就别走浏览器。公开信息优先用 WebFetch 或 API；浏览器留给「必须点界面才能验收」的情况。
    4.
